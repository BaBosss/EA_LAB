## ปัญหาที่กฎปัจจุบันไม่ครอบ

bar table ทุกวันนี้วัด **ผลรวมของ EA** (PF/DD/ruin/trades) ซึ่งถูกต้องสำหรับ *สัญญาณ* แต่
**วัด guard ไม่ได้เลย** เพราะ guard ที่ไม่เคยติดในหน้าต่างที่ทดสอบ จะให้ตัวเลข**เท่ากับ base
ทุกหลัก** แล้วผ่านทุกด่านโดยอัตโนมัติ — ดูเหมือน "ไม่ทำร้าย" ทั้งที่ความจริงคือ "ยังไม่ถูกทดสอบ"

**หลักฐานที่ทำให้เสนอ (ของจริง ไม่ใช่สมมุติ):**

| | |
|---|---|
| NuiIndy `CutLoss=30` (**เงินจริง** magic 1524) | run 2024 เท่า base ทุกหลัก (PF 2.20 · 836t · net 2,689.34) เพราะ DD ปีนั้นไม่แตะ 30% ⇒ guard ไม่เคยติด · ปี 2022 (ปีที่ควรติด) **ไม่มี base control** ⇒ **ไม่มีหน้าต่างไหนเลย**ที่พิสูจน์ว่ามันช่วย |
| MacroGate (ORDER-211) | "eqDD −54..−56%" วัดผ่าน classifier ที่พัง — gate ปิดประตูถี่เกินจริง ~75% ⇒ ประโยชน์ถูกประเมินสูงเกิน |
| MacdDiv `_02_MacdSignal` (ORDER-216) | ไม่ใช่ guard แต่กลไกเดียวกัน — input ที่ทำอะไรไม่ได้ สร้าง "plateau ไม่มีตัวขาดทุน" ที่เป็นจริงโดยอัตโนมัติ |

สามเคสนี้คือกลไกเดียวกัน: **ความเงียบของสิ่งที่ไม่เคยทำงาน ถูกอ่านเป็นหลักฐานว่ามันดี**

## ข้อความที่เสนอให้เติม (วางใน bar table ใต้แถว Model-4)

> | guard/filter/kill-switch (เมื่อจะนับเป็นหลักฐาน) | ต้องมี **base control run** ในหน้าต่างที่ guard *ควร* ติด **และ** ต้องรายงาน **จำนวนครั้งที่มันติดจริง** · ติด 0 ครั้ง = `UNTESTED` ห้ามเขียนว่าผ่าน · เลขที่เท่ากับ base ทุกหลัก = หลักฐานว่า **inert** ไม่ใช่หลักฐานว่า **ปลอดภัย** |

และเติมใน Row-X write-checklist อีก 1 บรรทัด:

> - [ ] ถ้า verdict อ้างประโยชน์ของ **guard/filter** ใดๆ — ระบุจำนวนครั้งที่ guard ติด + path ของ base control run

## ทำไมต้องเป็นกฎ ไม่ใช่แค่ memory

memory เตือนได้เฉพาะตอนที่ AI บังเอิญนึกถึง แต่เคสนี้**หลอกได้แนบเนียนเพราะมันผ่านทุกด่านจริงๆ** —
ไม่มีขั้นตอนไหนใน ladder ที่บังคับให้ถามว่า "guard ติดกี่ครั้ง" คนที่เดิน ladder ครบทุกข้ออย่างซื่อสัตย์
ก็ยังจะสรุปผิดอยู่ดี นี่คือเงื่อนไขของกฎ ไม่ใช่ของ heuristic

## ขอบเขต — สิ่งที่กฎนี้ **ไม่** ทำ

- ไม่บังคับให้รัน base control ย้อนหลังกับทุก guard ที่ deploy ไปแล้ว (แพงและส่วนใหญ่เป็น demo)
  — บังคับเฉพาะตอนที่ **จะเขียน verdict ที่อ้างประโยชน์ของ guard**
- ไม่เปลี่ยนสถานะ EA ตัวไหนย้อนหลัง — NuiIndy ยังเป็น user lane เหมือนเดิม เรื่องนี้แค่บอกว่า
  คำแนะนำ `CutLoss=30` มีหลักฐานอ่อนกว่าที่เคยเขียน ไม่ได้แปลว่ามันผิด
