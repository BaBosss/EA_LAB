## A. ก่อนเชื่อผลการวัด

**A1 · เครื่องมือคืน 0 = รันพัง จนกว่าจะพิสูจน์ว่าไม่ใช่**
Model 4 คืน **0 ไม้** ⇒ ผมสรุปว่า tick เสีย แล้ว**สั่งให้ user ไปโหลด history ใหม่** · user ทำจริง
และรันหลังโหลดให้ตัวเลข error **เท่ากันทุกหลัก** (58224 / 214709) = ข้อมูลไม่เคยเป็นตัวแปร
สาเหตุจริงคือ **เพดาน RAM**: 6 เดือน = 704 Mb ทำงานได้ · 3 ปี = 1,984 Mb จากเพดาน ~2,000 ⇒ คืน 0 บาร์เงียบๆ
- **ห้ามสั่งงานใครจากอาการ ต้องหาสาเหตุก่อน** · การทดสอบที่แยกสมมติฐานได้มักถูกและเร็ว (ที่นี่คือ "หั่นหน้าต่างให้สั้นลง")
- **อย่าหยิบบรรทัด log ที่น่ากลัวที่สุด หยิบบรรทัดที่อธิบายผลลัพธ์ได้** — `ticks discarded` เป็นคำเตือนรายวัน
  ที่มีในรันที่**สำเร็จ**ด้วย ส่วนบรรทัดที่อธิบาย 0 บาร์คือตัวเลขหน่วยความจำที่อยู่ถัดไปสองบรรทัด
- **M4 สไลซ์ล้มเงียบเป็นรายชิ้นได้** — control ปี 2025 คืน 0 บาร์ในรอบแรก รันซ้ำอันเดิมผ่านทันที (69.8M ticks)
  ⇒ **ตรวจ `bars generated > 0` ทุกสไลซ์ก่อนรวม** · ไม่งั้นได้ผลรวมที่หายไปทั้งปีโดยไม่มีอะไรฟ้อง
  (ผมเกือบรายงานของ 3 ปีเทียบกับของ 2 ปี)

**A2 · "แก้แล้ว" ต้องพิสูจน์ที่ปลายทาง ไม่ใช่ที่บรรทัดที่แก้**
ORDER-351 แก้ parser ของกรงกันเลนแล้ว **กรงยังปิดอยู่** ด้วยเหตุที่สอง (สถานะถูกอ่านจากทั้งเซลล์)
จับได้เพราะบังเอิญเปิดเลนตัวเองแล้วเห็นว่าข้อความ hook ไม่เปลี่ยน ⇒ **ถ้าไม่สังเกต จะรายงานว่าเสร็จด้วยความมั่นใจเต็มที่**

**A3 · แยก "อ่าน input ไม่ออก" ออกจาก "ไม่มีอะไรต้องบังคับใช้" เสมอ**
สองอย่างนี้พิมพ์ออกมาหน้าตาเหมือนกันได้ แต่ความหมายตรงข้าม · กรงที่ปิดตัวเองแล้วรายงานเป็น NOTE = ไม่มีกรง

**A4 · prose ของมนุษย์ในช่องที่เครื่องอ่าน ปิดกรงได้เงียบๆ**
คอมเมนต์ `<!-- -->` ใต้หัวตาราง ⇒ parse 0 แถว (ปิดทั้งตาราง) · คำอธิบายต่อท้ายสถานะ ⇒ แถวนั้นมองไม่เห็น (ปิดทีละแถว)
⇒ **parser ที่อ่านไฟล์ที่มนุษย์แก้มือ ต้องดึง token ที่ต้องการ ห้ามเทียบทั้งช่อง** และต้องทนคำอธิบาย

## B. ก่อนเชื่อผลการ optimize

**B1 · ผลชนขอบกริดแบบ monotone = คำตอบอยู่นอกกริด ไม่ใช่ข้อสรุปเชิงโครงสร้าง**
ผมปิด ORDER-352 ว่า *"pyramid = regime bet"* จากกริด `AddAtAtr` 2.0-4.0 · **ยอดจริงอยู่ที่ 1.0 ซึ่งอยู่นอกกริด**
พอขยายกริดกลายเป็น plateau แท้ PF 3.99 ⇒ **ขยายกริดก่อน อย่าเพิ่งสรุป** และอันตรายของมันคือ
มันมาพร้อมคำอธิบายที่ฟังขึ้น จึงหยุดการทดลองได้สนิท

**B2 · แกนที่ให้ผลเท่ากันทุกหลัก = ตรวจก่อนว่าเป็นเรื่องเครื่องมือหรือเรื่องกลยุทธ์**
`PbAtrMult` {0.5,1.0,1.5,2.0} ให้ผลเหมือนกันเป๊ะ ⇒ ตัด tester-cache ออกก่อนด้วยการ **grep `.set` + อ่านหน้า Inputs
ของรายงาน** ว่ารันด้วยค่าต่างกันจริง · พอตัดได้แล้วค่อยหาเหตุเชิงโครงสร้าง
(ที่นี่: stop อยู่บนเส้นห่าง 2.5 ATR ⇒ เกณฑ์ "ย่อ ≥ N ATR" ที่ N<2.5 เป็นจริงเสมอ — **stop กับตัวกรองวัดระยะเดียวกัน**)

**B3 · ยอดที่อยู่ริมหน้าผา ≠ ยอดที่ควรเลือก**
`ErMin` 0.30 ให้ PF 4.75 แต่ 0.32 ร่วงเหลือ 2.53 (ขยับ 0.02 = PF −47%) · 12 ไม้ที่หายไปเฉลี่ยไม้ละ +117
⇒ **เส้นที่พอดีเฉียดไม้กำไรก้อนใหญ่ไม่กี่ไม้ = overfit** ⇒ เลือก 0.25 (ศูนย์กลางที่ราบ) ยอมเสีย PF
**และตรวจเสมอว่าประโยชน์ส่วนไหนไม่ไวต่อค่า** — ที่นี่ BWD DD = 475.55 เท่ากันทุกค่า 0.20-0.40
⇒ **ประโยชน์ที่แข็งมาจากการเปิด gate ไม่ใช่จากค่าที่ตั้ง** ส่วนที่ไวต่อค่าคือส่วนที่ฟิตข้อมูล

**B4 · overlay ซ้อน overlay ต้องมี control ของชั้นล่างเสมอ**
MM + re-entry ให้ 2.47 ชนะ baseline 2.33 ⇒ ดูเหมือน re-entry เวิร์ค · แต่ MM เดี่ยวๆ ให้ **2.59**
⇒ **re-entry กินกำไรของ MM ไป 0.12** · ไม่มี control = ชั้นบนเคลมกำไรของชั้นล่าง

**B5 · แตกรายปีก่อนเชื่อ PF รวม**
PF 3.99 ทั้งหน้าต่างกลบไว้ว่า **มีปีขาดทุน 2 ใน 6 ปี** และกำไรเกือบทั้งหมดมาจาก 2 ปี

**B6 · เทียบที่ DD เท่ากัน ไม่ใช่ที่ lot เท่ากัน**
บน holdout กำไร 2 เท่าของ host เดิม แต่ DD 3 เท่า ⇒ **ที่ความเสี่ยงเท่ากัน host เดิมชนะ**
⇒ lever แบบ "เพิ่มขนาด/เพิ่มการมีส่วนร่วม" ทุกตัวต้องผ่านการเทียบแบบนี้ ไม่งั้นจะเข้าใจว่า leverage คือ edge

**B7 · MC ประเมิน DD ต่ำกว่าความจริง — ใช้ค่าที่วัดได้จริง**
bootstrap ให้ 99th = 2.89% · วัดจริง 7.61% · order-resampling ทำลาย serial correlation ที่เป็นตัวสร้าง drawdown
**และ MC โหมด default = permutation ซึ่ง PF คงที่** ⇒ บาร์ PF-5th อ่านจากโหมดนั้นไม่ได้ ต้อง `--bootstrap`

**B8 · guard/filter ต้องพิสูจน์ทั้งว่า "ติด" และ "เงียบถูกที่"**
ER gate ที่ 0.20 ตัด **0 ไม้บน MAIN** (เลขเท่ากันทุกหลัก) แต่ตัด **6 ไม้บน BWD** = specificity ที่ต้องการ
· **ตัด 0 ไม้ในหน้าต่างที่ควรตัด = `UNTESTED` ห้ามเขียนว่าผ่าน** · และถ้าจำนวนไม้เท่ากันเป๊ะ
ให้ดู **องค์ประกอบ long/short + gross แยกขา** ก่อนสรุปว่าเฉื่อย (filter เคยให้ 250=250 แต่สลับตัวไม้ทั้งชุด)

**B9 · หลักฐานจากหน้าต่างที่ใช้จูน ไม่ใช่หลักฐาน**
`ErMin` ถูกเลือกโดยดู BWD ⇒ **BWD หมดสภาพเป็น out-of-sample ของค่านั้นทันที**
ต้องเขียนกำกับไว้ทุกครั้งที่อ้างตัวเลขนั้น ไม่ใช่จำเอา

## C. ก่อน + หลัง attach

**C1 · `_06_AllowLive` และ magic — อ่านย้อนกลับจากแท็บ Inputs ของชาร์ตจริงเสมอ**
`.set` ที่ bundle มาตั้ง `AllowLive=false` ⇒ `990025` **นิ่ง 3 วันโดยดูปกติทุกอย่าง**
· ครั้งนี้แก้ใน bundle แล้ว **แต่ยังต้องอ่านย้อนกลับ** เพราะ cache ของ terminal ทับ input ที่ไม่ได้ระบุได้
· **magic ที่ผิดอันตรายกว่า** เพราะไม่มีอาการเลย: ดีลไปผูกกับ magic ที่ไม่มีใครเฝ้า และ `DEPLOYMENTS.csv`
จะชี้ไปที่ magic ที่ไม่มีไม้ตลอดกาล **โดยไม่มีอะไรฟ้อง**

**C2 · `.ex5` ตรวจด้วย mtime ไม่ใช่ hash** — MQL5 compile ไม่ byte-reproducible ⇒ hash ต่างไม่ได้แปลว่าโค้ดต่าง
· และ **input ที่หายไปจากหน้า Inputs** คือสัญญาณว่าโหลด binary เก่า (ขนาดไฟล์เชื่อไม่ได้)

**C3 · `.ex5` ติด `.gitignore`** ⇒ bundle ใน repo **ไม่มี binary** · ต้องเขียนบอกใน README ไม่งั้น clone ใหม่จะได้ของไม่ครบ

**C4 · แผนกับของจริงต่างกันได้ — record ต้องตามของจริง**
บันทึกไว้ว่า attach ที่ `415573666` · ของจริงลง `463666728` (เห็นจากภาพหน้าจอ)
⇒ **แก้ record ตามของจริงทันที** และ **ผลข้างเคียงต้องตามไปด้วย**: คู่ A/B กลายเป็นคนละ terminal
⇒ ชนกฎห้ามเทียบข้าม install (ORDER-371) ⇒ **เทียบ PF ตรงๆ ไม่ได้แล้ว** แต่คำถามเชิงพฤติกรรมยังตอบได้

**C5 · นาฬิกา judge เริ่มที่ไม้แรกที่เทรดจริง ไม่ใช่วัน attach** — `990025` ต้อง re-base เพราะข้อนี้

**C6 · ขาที่สัญญาณ+สินค้าเดียวกัน = คู่ A/B ไม่ใช่การกระจายความเสี่ยง**

## D. เรื่องบันทึก

**D1 · ตรวจวันที่จาก `git log` ไม่ใช่จากความจำ** — เซสชันนี้คร่อมสองวัน ผมลงวันที่ผิด 2 ใบ
· `B1_DATASET.csv` เป็น append-only **ไม่มีทางออกที่รับรอง** ⇒ แก้ไม่ได้ ต้อง append แถวบันทึกความคลาดแทน

**D2 · ทำงานต่อหลังปิดเลน ต้องพลิกแถวกลับเป็น `ACTIVE` ก่อนแตะไฟล์** — `CLOSED` ไม่ได้แปลว่า "เขียน handoff แล้ว"
แต่แปลว่า "กรงกันชนหยุดทำงานแล้ว"

**D3 · เมื่อกรงรายงานว่า "ข้ามกฎ" อย่าเดาสาเหตุจากสิ่งที่ตัวเองเพิ่งทำ**
เลนหนึ่งเห็นข้อความแล้วโทษว่าตัวเอง mark CLOSED (เพราะเพิ่งทำพอดี) — คำอธิบายที่สมเหตุสมผลและ**ผิด**
· สาเหตุจริงคือ parser bug ที่มีมาก่อนหน้านั้นหนึ่งวัน ⇒ **ยาที่เขาเขียนไว้ใช้ไม่ได้จริง**

**D4 · commit ล้มจาก stale lock ได้** — `next-index-<pid>.lock` ค้างข้ามวัน ⇒ process ใหม่ที่ได้ PID ซ้ำจะชน
· ตรวจว่า PID ตายจริง + ไม่มี git รันอยู่ ก่อนลบ · และ **ระหว่างที่ commit เราล้ม เลนอื่นอาจ commit งานเราติดไปด้วย**
(path-limit กันข้าม*ไฟล์* ไม่กันข้าม*บรรทัด*ในไฟล์เดียวกัน) ⇒ เนื้อไม่หาย แต่ provenance เพี้ยน ต้องเขียนบอก
