> **⚠️ RELIABILITY MODEL UPDATED 2026-07-12 (Codex re-review r2 → FAIL-CLOSED DEFAULT).**
> The model flipped from a blacklist ("exit-unreliable set", default reliable) to a **whitelist**:
> `run_batch.ps1` trusts a runner's exit code **only** if its basename is in the reliable whitelist
> **`{mt5_run.ps1, mock_runner.ps1}`** (or the job sets `exit_reliable:true`). **Every other runner —
> `mt4_run`, all optimizers, and all batch drivers (`mass_smoke_*`, `mt5_batch_shortlist`,
> `qwen_batch_runner`), plus any unknown/new runner — now defaults to exit-UNRELIABLE** and must
> produce positive success evidence (an `OK( OPT)? REPORT|OK OPTIMIZER XML` marker OR a satisfied
> `expect_artifact`); exit 0 with no evidence = FAILED. This means the per-row notes below that say a
> batch runner is "NOT in the unreliable set / default reliable / should set `exit_reliable:false`" are
> **SUPERSEDED** — those runners are handled fail-closed automatically now (setting `exit_reliable:false`
> is redundant but harmless; you'd only ever set `exit_reliable:true` to *opt back into* trusting a
> non-whitelisted runner's exit code).

## Notes for run_batch.ps1 (Phase 2 + Phase 4 false-green fix + 2026-07-12 reliability-model fix)

- **Exit code alone is NOT trustworthy across this fleet** (see the reliability column above — only `mt5_run.ps1` sets a distinct, correct code on every branch). `run_batch.ps1` therefore treats a job as "done" only if ALL of: (a) `$LASTEXITCODE -eq 0`, (b) the runner's captured stdout+stderr does NOT match `/NO( OPT)? REPORT|NO XML|ABORT|ERROR|FATAL/i`, (c) the job's optional `expect_artifact` glob (when given) matches a file with `mtime >= job start`, and (d) for a runner on the built-in **exit-unreliable basename set** (`mt4_run.ps1`, `mt4_optimize.ps1`, `mt5_optimize.ps1` — or any job explicitly marked `"exit_reliable": false`), POSITIVE success evidence: stdout matching `/OK( OPT)? REPORT|OK OPTIMIZER XML/i`, or a satisfied `expect_artifact`. This is what catches `mt4_run.ps1`'s documented false-green (prints `NO REPORT` but falls through to exit 0), the analogous gap in both optimizer scripts, **and the 2026-07-12 regression** where `mt4_optimize.ps1`'s real wording `NO OPT REPORT` slipped past the old narrower `NO REPORT`-only pattern and — absent an `expect_artifact` — would have been silently marked done. `run_batch.ps1` still never adds a second KILL layer — it only launches each runner via `powershell -File <runner> @args`, reads `$LASTEXITCODE`, and reads back the captured stdout; it never terminates the process itself (that remains each runner's own responsibility, see the timeout/kill column above).
- **Reliability model**: a job's runner is treated as exit-UNRELIABLE if either (1) the job manifest sets `"exit_reliable": false` explicitly, or (2) no override is given and the runner path's basename case-insensitively matches `mt4_run.ps1`, `mt4_optimize.ps1`, or `mt5_optimize.ps1`. Everything else (including `mt5_run.ps1` and the test mock) defaults to exit-reliable, where the plain (a)+(b)+(c) checks are sufficient and no positive marker is demanded. `"exit_reliable": true` on a job forces the lenient path even for a runner on the built-in list, for the rare case a caller has independent proof the exit code is trustworthy for that specific invocation.
- Lane = install identity (an exe path / a terminal instance), not just "MT5 vs MT4" — two portable installs of the same platform are two independent lanes; two jobs pointed at the same install are the same lane and must not run concurrently (the runners' own same-install guards would otherwise ABORT with exit 2, which run_batch must treat as a hard failure, not silently retry). The advisory lane lock `run_batch.ps1` takes lives at a **fixed GLOBAL path** (`$env:TEMP\ealab_run_batch_locks\lane_<sanitized>.lock`), independent of the caller's `-StateDir`, so two separate `run_batch.ps1` invocations aimed at the same physical lane from different `-StateDir` values still mutually exclude.
- `-Model 4` (every-tick) jobs are the slow/heavy ones; per repo convention they run on the lane-1/serial install, never the parallel "b" lane. `run_batch.ps1` checks this PHYSICALLY when possible: if a job's `args` carry an explicit `-Terminal` value, that value must equal `-Lane1Terminal` (default `D:\Meta 5\terminal64.exe`), regardless of what the job's `lane` label says (a manifest could otherwise claim `lane: "fake-1"` while actually pointing `-Terminal` at the lane-2 install). Only when no `-Terminal` arg is present does it fall back to the lane-label check (`"1"`, `"lane1"`, or anything ending `-1`).
- Manifest job `id` values must be unique — `run_batch.ps1` validates this as a pre-flight check (aborts exit 2, naming the duplicate, before any job runs) because the id→job lookup used during execution picks the first match and a duplicate would silently run the wrong runner for one of the two ids.
- `state.json` is written atomically (temp file + `Move-Item -Force` rename) so a crash mid-write never leaves a truncated file; on load, a missing/empty `state.json` means a fresh run, but a `state.json` that exists and fails to parse as JSON aborts loudly (exit 2) rather than silently discarding resume history.
