## Notes for run_batch.ps1 (Phase 2)

- Every runner above already owns its own timeout + (where present) self-kill-on-timeout logic scoped to the ONE process IT launched. `run_batch.ps1` must never add a second kill layer — it only launches each runner via `powershell -File <runner> @args` and reads `$LASTEXITCODE` (or absence of expected output, for the runners that don't set an explicit exit code on every branch — treat "no error text keywords + no crash" as best-effort, but for MVP-0 purposes the mock runner always returns an explicit exit code so `$LASTEXITCODE` is the single source of truth for job pass/fail).
- Lane = install identity (an exe path / a terminal instance), not just "MT5 vs MT4" — two portable installs of the same platform are two independent lanes; two jobs pointed at the same install are the same lane and must not run concurrently (the runners' own same-install guards would otherwise ABORT with exit 2, which run_batch must treat as a hard failure, not silently retry).
- `-Model 4` (every-tick) jobs are the slow/heavy ones; per repo convention they run on the lane-1/serial install, never the parallel "b" lane, so `run_batch.ps1`'s manifest schema carries an explicit `model` field to let callers assert/guard this placement.
